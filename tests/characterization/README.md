# 現行コードの計算結果の記録

リニューアルで計算ロジック（順位、合計、勝ち抜け、優勝、個人成績の分析など）を書き直すときに、
「現行コードが何を返していたか」と突き合わせるための記録。

## 何を記録しているか

`models/` の全クラスの public static メソッドのうち、読み取り系の全部を、シード（`db/seed_data.sql`）に
対して全パラメータの組み合わせで呼び、その戻り値を 1 呼び出し 1 行で保存している。

- 記録: `golden/legacy/seed.jsonl`
- 書き出しスクリプト: `legacy-export.php`（呼び出す対象と、除外するメソッドの一覧を持つ）
- 実行と照合: `run.mjs`

書き込み系のメソッドは `legacy-export.php` の `EXCLUDED` に理由つきで挙げてあり、ここでは呼ばない。
モデルに public static メソッドを追加したら、書き出し対象か `EXCLUDED` のどちらかに加える
（どちらにも無いと書き出しが失敗する）。

## 使い方

Docker が動いていれば、E2E 専用スタック（`docker-compose.test.yml`）の起動とシードの入れ直しは自動で行われる。

```bash
# 今のコードが記録と同じ結果を返すかを確かめる
node tests/characterization/run.mjs check

# 記録を作り直す（シードやモデルを意図して変えたとき）
node tests/characterization/run.mjs capture

# 別の環境（別の PHP バージョンのイメージなど）で legacy-export.php を実行した結果を照合する
node tests/characterization/run.mjs check path/to/export.jsonl
```

`check` が落ちたら、まず差分を読む。意図した変更なら理由を PR に書いたうえで `capture` し直す。
意図していない差分なら、記録ではなくコードを直す。

## 記録の形式

| 行の形 | 意味 | 照合のしかた |
|---|---|---|
| `{"call","args","result"}` | 条件を変えても毎回同じ結果 | 完全一致 |
| `{"call","args","unstable":"order","result"}` | 並び順が実行によって変わる。または、同じメソッドの別の呼び出しで結果の変化が見つかった。`result` は並び順を正規化した値 | 並び順を正規化して一致 |
| `{"call","args","unstable":"content","variants"}` | 内容が実行によって変わる。`variants` は観測した結果の一覧 | 一覧のどれかと一致 |

戻り値が例外だった場合は `result` の代わりに `error` が入る。

## 結果が変わる呼び出しについて

現行コードには、同じデータでも結果が変わる呼び出しがある。SQL が同点のときの並び順や、
複数の候補から選ぶ 1 行を決めていないためで、PostgreSQL の実行計画や行の物理的な並びによって結果が変わる。

`capture` は、プランナの設定（`PGOPTIONS`）と行の物理的な位置を変えながら複数回書き出し、
結果が変わった呼び出しに `unstable` の印を付ける。条件の一覧は `run.mjs` の `CONDITIONS`。
原因は SQL の側にあるので、1 件でも変わったメソッドは、その回に変わらなかった呼び出しも
並び順に依存しない形で記録する。条件を変えて何度も書き出すため、`capture` には 15 分ほどかかる
（`check` は 1 回の書き出しで済み、30 秒ほど）。

印の付いた呼び出しは、現行の振る舞いが 1 つに決まっていない箇所なので、新しいコードでは
ルール（同点時の順位、優勝者の決め方など）を定義して決める。定義は `docs/renewal/domain-rules.md` に書く。

この方法で見つかるのは、シードのデータで実際に差が出たものだけである。同点のデータがシードに無い
箇所の不安定さは見つからない。

## 制約

- シードは開発用のデータで、本番のデータではない。本番のデータでの記録は別に取る（リポジトリには入れない）。
- 記録しているのはモデルの戻り値までで、ページ側で行っている計算（率の算出など）は含まない。
- 書き込み系の処理（成績の確定、勝ち抜けの判定など）は含まない。
